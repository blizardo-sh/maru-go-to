# Выпуск и восстановление

Пользователь принял 21 октября 2026: `https://outboundserver.freemyip.com/`, CI для PR и автоматический выпуск из `main`, RPO ≤ 1 час и RTO ≤ 4 часа после обнаружения аварии. [ADR-0006](adr/0006-share-https-with-existing-vpn.md), [ADR-0007](adr/0007-hourly-offsite-recovery.md).

## Топология и защита

Существующий сервер: Ubuntu 22.04, amd64, 1 CPU / 2 GB RAM; перед установкой измерено около 1.3 GiB доступной RAM и 6.3 GiB свободного диска. Сборки выполняются на GitHub, существующий Docker не обновляется.

Nginx принимает публичный 443 и различает SNI: `outboundserver.freemyip.com` → HTTPS на `127.0.0.1:9443`, остальные подключения → Xray на `127.0.0.1:443`. У VPN сохраняется публичный порт 443 и прежние параметры клиентов; PROXY protocol сохраняет адрес клиента. OpenGym остаётся на 8443. Перенос Xray на другой номер порта отклонён: он изменил бы новые VPN-подписки.

Nginx завершает TLS существующим сертификатом и направляет HTTP на Caddy `127.0.0.1:8081`. Caddy раздаёт `dist` и передаёт API во внутреннюю сеть Compose; порты API и PostgreSQL не публикуются. Nginx перезаписывает IP-заголовки, Caddy передаёт единственный доверенный IP в Better Auth, чтобы нельзя было обойти лимит поддельным `X-Forwarded-For`. Ограничены также приглашения и восстановление пароля, обслуживаемые вне Better Auth.

Контейнеры API и web работают без root, с read-only filesystem, сброшенными capabilities, ограничениями RAM/PID и ротацией журналов. PostgreSQL хранит данные в постоянном volume; runtime-пользователь имеет только DML-доступ к публичным таблицам, а миграции выполняются отдельно администратором БД. Пароли, ключи и строка миграции находятся только в `/opt/japanese-learning/.env` с правами root:600. TLS ограничен 1.2/1.3, выставлены HSTS, CSP и запрет встраивания страницы. `/ready` доступен через локальный web, публичный `/health` не содержит конфигурации.

## CI/CD

[Delivery](../.github/workflows/delivery.yml):

1. PR: frozen install Bun 1.4.3, typecheck, dependency audit, миграции и все тесты на одноразовой PostgreSQL 18.6, Vite build, проверка подготовительных файлов, browser-проверка приглашения/входа/выхода, проверка SSH-команды. Секрет деплоя PR не передаётся.
2. После merge в `main`: сборка Linux/amd64 API и web, публикация в `ghcr.io/blizardo-sh/maru-go-to-{api,web}:<commit>`.
3. SSH с закреплённым host key и отдельным `DEPLOY_KEY`. Учётная запись `japanese-deploy` не имеет shell, forwarding, PTY или Docker-доступа; разрешена только команда `deploy <полный SHA>` через root-owned wrapper.
4. Временный `GITHUB_TOKEN` передаётся по stdin для чтения GHCR, конфигурация registry удаляется сразу после загрузки. SHA проверяется также в OCI label, на сервере сохраняются digest обоих образов.
5. Перед миграцией — успешная внешняя копия. Затем миграция отдельной командой, `compose up --wait`, readiness, новая внешняя копия и проверка восстановления в отдельную БД. Неуспешный выпуск возвращает предыдущие образы; схема автоматически назад не откатывается.
6. Workflow проверяет публичный HTTPS и закрытый доступ к `/api/me` без сессии. Повторный ручной выпуск доступен через `workflow_dispatch` на `main`; параллельные выпуски сериализованы.

Сборки не получают production-пароли. Адрес SSH и закреплённые host keys находятся в Actions secrets `DEPLOY_HOST` и `DEPLOY_KNOWN_HOSTS`, адреса серверов не включаются в исходники; закрытый `/etc/japanese-learning/host.env` содержит параметры хоста и внешних копий. Action SHA и базовые Docker digest закреплены. Обновление этих pins — отдельное проверяемое изменение. Начальная конфигурация хоста устанавливается вручную из `deployment/provision.sh`; изменения host-side скриптов и Compose требуют повторной установки конкретных файлов администратором, workflow обновляет образы приложения.

## Первоначальная установка

`deployment/provision.sh` — одноразовый скрипт от root из каталога deployment с двумя аргументами: файл публичного deploy-ключа и закрытый `host.env` с `DOMAIN`, `PUBLIC_IPV4`, `BACKUP_HOST`. Он отказывается заменять существующую конфигурацию, создаёт случайные независимые секреты, ограниченную SSH-учётную запись и отдельный зашифрованный restic-репозиторий на втором сервере. До изменения слушателей сохраняет SQLite через backup API и конфигурацию nginx, включает трёхминутный автоматический откат. Откат отменяется только после сквозного запроса через VPN, проверки TLS и health OpenGym. Исходные ключи VPN не меняются и в репозиторий не включаются.

После первого успешного выпуска администратор создаёт приглашение:

```sh
cd /opt/japanese-learning
docker compose --env-file .env --env-file release.env -f compose.yaml run --rm --no-deps api bun src/server/admin.ts bootstrap owner@example.com
```

Ссылка действует один раз; пароль задаёт владелец. Письма автоматически не отправляются. Внешний ИИ по умолчанию выключен; настройка провайдера и ключа выполняется отдельно в защищённом `.env`, после неё нужен перезапуск API. Подготовленные разборы и остальные учебные функции работают без внешнего ИИ.

## Резервные копии

`japanese-backup.timer` запускает копию каждые 30 минут, оставляя запас для целевого RPO ≤ 1 час. Сохраняются согласованный `pg_dump -Fc`, секреты выпуска, Compose, nginx и эксплуатационные скрипты. Данные шифруются restic до передачи по SFTP на второй имеющийся сервер; SSH host key закреплён. Хранятся часовые снимки за 7 дней и ежедневные за 30 дней. Работа идёт с отдельным repo `/repo/japanese-learning` и не меняет VPN-копии.

`japanese-backup-verify.timer` ежедневно в 04:15 UTC (07:15 Москвы) читает все зашифрованные блоки, скачивает последний снимок и восстанавливает dump во временную БД с уникальным именем. Проверяет схему и сообщает количество пользователей, расписаний и попыток; production-база не заменяется. Проверка выполняется также при каждом выпуске. Внешний статус обновляется только после успешной копии; пропущенная копия и ошибка восстановления видны как failed systemd unit. Оповещения во внешние сервисы не настроены.

Команды от root:

```sh
/usr/local/sbin/japanese-backup backup
/usr/local/sbin/japanese-backup verify
/usr/local/sbin/japanese-backup status
systemctl list-timers 'japanese-*'
journalctl -u japanese-backup.service -u japanese-backup-verify.service --since today
```

Пароль расшифровки — существующий `/etc/vpn-maintenance/restic-password`; его независимая копия уже входит в закрытые архивы восстановления VPN на Mac. Без этого пароля копия бесполезна. Восстановление на новом сервере: подготовить безопасный SSH/SFTP-доступ и пароль, проверить `restic check --read-data`, восстановить конфигурацию и dump в отдельный каталог, поднять PostgreSQL той же major-версии, создать роли и восстановить данные, затем запустить закреплённые digest приложения и проверить вход/прогресс/HTTPS. Не применять новые миграции до проверки исходной версии.

## Откат и границы

`/opt/japanese-learning/previous.env` сохраняет предыдущие digest. Для отката после проверки совместимости схемы вернуть его как `release.env` и выполнить Compose `up -d --wait`. Не выполнять `down -v`, не менять major PostgreSQL поверх существующего volume. Полное восстановление VPS требует также возврата DNS, TLS, SSH и VPN; целевой RTO 4 часа не является подтверждённым временем такого учения. Проверка dump на работающем VPS измеряет только часть восстановления.

Исходная сеть сохранена в `/var/lib/japanese-provision/`; её rollback-скрипт временно перезапускает nginx и VPN. Использовать его только для возврата всей исходной топологии, а не обычного отката приложения.

Один VPS не обеспечивает непрерывную доступность при потере самого сервера. Нагрузка 10 учеников и внешняя AI-квота требуют отдельных измерений. Результаты первого фактического выпуска добавляются после проверки.
