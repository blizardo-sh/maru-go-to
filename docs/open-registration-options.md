# Открытая регистрация и восстановление доступа

Статус: реализовано в ветке `feat/open-registration`, ещё не развёрнуто. 5 ноября 2026 года пользователь согласовал Q4 (новые ученики подтверждают почту до доступа) и Q5 (существующие сохраняют доступ, подтверждают адрес после входа; до этого восстановление только через администратора). Gmail проверен с локальной машины: пользователь подтвердил одно тестовое письмо во «Входящие» Mail.ru.

## Подтверждённые требования

- Q1: изменение относится к японскому тренажёру, не к OpenGym.
- Цель пользователя: регистрация без приглашений и возможность сбросить забытый пароль.
- Владелец не хочет обслуживать собственный почтовый сервер или дополнительно платить.
- Q2: бесплатная внешняя отправка писем допустима; после сравнения предложена проверка отдельного Gmail.
- Пользователь самостоятельно зарегистрировал `marugoto.learning@gmail.com` для отправки писем тренажёра и сохранил пароль приложения в локальном файле, исключённом из Git. Пользователь разрешил одно тестовое письмо на свой адрес Mail.ru; отправка и попадание во «Входящие» подтверждены. Пароль не включается в документацию или Git.

## Исходное состояние

Вход по email и паролю работает через Better Auth. Открытая регистрация отключена. Администратор выдаёт ссылки восстановления вручную; в базе хранится хеш токена, срок ссылки — один час, успешный сброс отзывает сессии. Существующие аккаунты сохраняют учебное состояние.

Владение историческими email не всегда проверялось: общая регистрационная ссылка создаёт неподтверждённый адрес, персональное приглашение выставляет `email_verified=true` без автоматического письма. При переходе нельзя считать этот флаг доказательством владения ящиком. Автоматическое восстановление или объединение со внешним входом по одному совпавшему email может передать чужой прогресс владельцу ошибочно указанного адреса. Принятая мера: привязка подтверждённого канала из текущего аккаунта после повторной аутентификации; для потерявших доступ заранее — отдельный ручной переход.

Последний локальный отчёт о выпуске указывает основной адрес `https://94.103.2.98`; прежний DDNS — `outboundserver.freemyip.com`. Наличие собственного домена с полноценным управлением DNS не установлено.

## Проверка отправки

С локальной машины выполнено TLS-подключение к `smtp.gmail.com:465` с проверкой сертификата, аутентификация паролем приложения и отправка одного согласованного тестового письма. Gmail подтвердил приём; пользователь отдельно подтвердил попадание письма во «Входящие» Mail.ru. Секрет не выводился в журналы, локальный файл имеет права `0600` и исключён из Git. Первая попытка из песочницы остановилась на DNS до подключения; письмо отправлено один раз после разрешённого сетевого запуска.

Это подтверждает работоспособность конкретного отправителя и один случай доставки. Отправка с production-сервера, письма с настоящими ссылками подтверждения/сброса, другие получатели, нагрузка и долговременная доступность ещё не проверены.

## Принятое поведение

Открытая форма `/register`: имя, email и пароль 8–128 символов. Учётная запись всегда обычная, без назначения администратора. До подтверждения адреса вход и защищённый API закрыты. Повторная регистрация по существующему адресу возвращает такой же ответ, не меняя имя, пароль, роль или прогресс. Старые приглашения остаются совместимыми, но также требуют подтверждения почты.

Миграция `0007_email_access` снимает исторический `email_verified`, поскольку приглашение не доказывало владение почтой. Флаг `email_verification_required=false` сохраняет существующим ученикам вход, сессии и данные. Войдя, ученик открывает «Подтвердить почту», повторно вводит текущий пароль и подтверждает адрес по письму. Публичная повторная отправка не включает восстановление для старого неподтверждённого аккаунта. Если пароль уже потерян, администратор выдаёт индивидуальную ссылку восстановления.

`/forgot-password` отправляет ссылку только на подтверждённый адрес. Публичный ответ одинаков для отсутствующего, неподтверждённого и подтверждённого аккаунта. Подтверждение и сброс используют разные одноразовые токены на один час; в базе хранится SHA-256, URL содержит токен во фрагменте. Открытие страницы не расходует ссылку: нужна кнопка и POST. Успешный сброс отзывает все сессии и незавершённые подтверждения адреса. Новое письмо заменяет старую ссылку того же назначения.

Письма уходят через SMTP с TLS, без собственного почтового сервера. Ограничения хранятся в PostgreSQL и переживают перезапуск: 10 публичных запросов в минуту на IP, 100 регистрационных запросов в час на приложение; одно письмо данного назначения на адрес в минуту и три в час; отдельные бюджеты 150 подтверждений и 50 восстановлений за 24 часа. Проверка пароля старого аккаунта ограничена пятью попытками за 15 минут. Ошибки отправки также расходуют бюджет; интерфейс предлагает повторный запрос. Эти пределы — защитные настройки приложения, а не обещание Gmail о доставке.

SMTP выполняется после HTTP-ответа, чтобы время ответа не раскрывало наличие аккаунта. На штатном завершении приложение дожидается текущих отправок. Очередь не сохраняется между аварийными перезапусками; пользователь запрашивает письмо снова. Журналы не содержат SMTP-пароль, токены и содержимое письма. Без SMTP-настроек вход существующих учеников работает, регистрация и запрос письма возвращают 503.

## Подготовка выпуска

1. Сохранить резервную копию базы. Настроить `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM` в защищённом серверном env-файле; пример находится в `.env.example`. Для Gmail используется пароль приложения, без группирующих пробелов. Файл с настоящим секретом не передаётся в Git и образ.
2. Проверить `APP_URL`: ссылки строятся только из этого доверенного адреса. Обновить контейнеры, применить миграцию и конфигурацию nginx из `deployment/nginx-http.conf`. nginx перезаписывает IP-заголовок, Caddy передаёт только это значение, API не публикуется напрямую.
3. Выполнить согласованный сквозной тест с сервера: регистрация → письмо → подтверждение → вход → сброс → новый вход. Тестовая отправка с ноутбука не проверяет исходящий SMTP с VPS и письмо с настоящим URL.

Новые реальные тестовые письма требуют согласованного получателя и назначения. Локальные API- и браузерные проверки перехватывают почту в памяти на адресах `example.test`.
