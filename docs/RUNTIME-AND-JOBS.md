# Hono, Bun и фоновые задачи

Статус: исследование завершилось выбором пользователя 20 октября 2026 года — Hono + Bun, PostgreSQL, без брокера. Действующие версии и локальные результаты — в [матрице совместимости](STACK-COMPATIBILITY.md); архитектура — в [ARCHITECTURE.md](ARCHITECTURE.md). Сравнение ниже объясняет альтернативы, а не требует повторно выбирать runtime. Linux/VPS-нагрузка и Q36 о восстановлении пока не подтверждены.

## Независимые решения

Hono — HTTP-framework; Bun — среда исполнения JavaScript/TypeScript и набор инструментов. Hono работает и на Bun, и на Node.js. Выбор Hono не требует Bun; выбор package manager также не определяет production-runtime. Основной frontend-кандидат React / TypeScript / Vite от этого сравнения не меняется.

| Связка | Подтверждённые свойства | Инженерная оценка для проекта |
| --- | --- | --- |
| Hono + Node.js 24 LTS | Fetch-интерфейс через `@hono/node-server`; middleware; validator/RPC; отдельное расширение для Zod/OpenAPI; документирован graceful shutdown | Рассмотренная альтернатива; пользователь выбрал Bun |
| Hono + Bun | Нативный Fetch-сервер Bun, streaming и управление завершением процесса; Hono не требует другого framework | Принят; выбранные auth, драйвер, миграции и библиотечные операции проверены локально, Linux отдельно остаётся к проверке |
| Elysia + Bun | Framework ориентирован на Bun; схемы runtime-валидации, OpenAPI plugin и типизированный клиент Eden; есть адаптеры других платформ | Альтернатива при предпочтении тесно связанного framework/client. Сравнение с Hono нужно вести на учебном API, а не по таблице HTTP-скорости |
| NestJS + Node.js | Архитектурные соглашения, DI, модули, HTTP-адаптеры и официальный OpenAPI-инструмент | Остаётся вариантом, если команда предпочитает заданные framework правила. Для пяти предметных областей автоматического преимущества перед явными модулями Hono нет |

Node рекомендует Active/Maintenance LTS для production; на дату проверки 24 находится в LTS. Эта альтернатива была рассмотрена до выбора пользователя. Для принятого Bun точные версии уже закреплены и проверены по отдельной матрице; измеренной экономии памяти относительно Node по-прежнему не заявлено.

## Что действительно даёт Hono

Hono RPC выводит TypeScript-типы запросов и JSON-ответов из описания маршрутов. Это удобство собственного TS-клиента; оно не проверяет произвольный JSON от внешнего ИИ и не обеспечивает права пользователя. Глобальные ошибки middleware и `onError` требуют явного включения в типизированный контракт. Для внешне читаемого интерфейса есть официальный пример `@hono/zod-openapi`: явные схемы дают проверку запросов и OpenAPI. Описание response schema не является доказательством автоматической проверки каждого исходящего значения.

Better Auth документирует интеграцию с Hono через Web Request/Response без дополнительного адаптера. Drizzle-адаптер Better Auth поддерживает PostgreSQL. Это подтверждает путь интеграции, но ручные одноразовые приглашения, восстановление, проверка владельца и управление сессиями приложения всё равно требуют реализации и проверки.

Предметные операции располагаются в модулях учётных записей, корпуса, практики/повторений, личных слов и свободного разбора. HTTP-маршруты проверяют схемы, получают пользователя и вызывают эти операции. Транзакция повторения и проверка упражнения имеют небольшие интерфейсы, доступные тестам без HTTP. Именно этот контракт предотвращает накопление логики в обработчиках; выбор Hono сам его не создаёт.

## Условия выбора Bun

1. **Зависимости.** Проверить на закреплённом runtime авторизацию, hashing, драйвер PostgreSQL, миграции, FSRS и инструменты диагностики. Bun документирует отличия некоторых Node API: например, низкоуровневых `async_hooks`, `worker_threads.resourceLimits` и профилирования. Из этого не следует конкретная несовместимость Better Auth; она не была обнаружена запуском.
2. **Версии драйвера и ORM.** Первоначальные страницы предлагали `@rc`, но stable Drizzle 0.45.4 уже экспортирует `bun-sql`; связка с Bun.SQL и Better Auth теперь проверена на реальной БД. Используются stable pins и соответствующие исходники. `bun-sql` привязывает драйвер к Bun; Node-переход потребует другой точки запуска и проверки драйвера.
3. **Таймауты.** У `Bun.serve` idle timeout по умолчанию 10 секунд, включая ожидание первых данных от handler. Он может оборвать долгий или замолчавший streaming-ответ. Согласованный p95 ИИ ≤ 10 секунд не является максимальной длительностью каждого запроса. Таймаут ИИ, лимиты HTTP/proxy, при необходимости heartbeat и прекращение запроса задаются явно; бесконечное ожидание не является решением.
4. **Завершение процесса.** При SIGTERM прекращается приём новой работы, активные операции получают ограниченное время завершения, затем закрываются соединения. Bun предоставляет `stop()` / `stop(true)`; сам факт наличия методов не подтверждает корректность нашего shutdown.
5. **Проверка типов.** Документация Bun содержит новые команды/флаги, не все из них работают на выбранном release; `--no-script` был отклонён Bun 1.4.3. В проверенном наборе явно выполняется закреплённый TypeScript CLI на Bun; автоматическое исполнение `.ts` не подменяет typecheck.

Официальные HTTP-бенчмарки характеризуют конкретные условия авторов. Например, сравнительная таблица на просмотренной странице Elysia ссылается на измерения 2023 года / Bun 0.7.2. Её нельзя выдавать за сравнение нашего приложения или текущих версий. Главное ограничение свободного разбора может оказаться у провайдера ИИ; смена runtime не повышает его квоту.

## Нужен ли брокер текущим потокам

Очередь задач хранит поручения, повторы и состояние выполнения. Брокер сообщений обеспечивает доставку между отправителями и получателями, маршрутизацию и подписки. Эти обязанности могут сочетаться в продукте, но являются разными потребностями. Учебное задание не становится фоновой задачей только из-за названия.

| Поток | Рекомендация | Причина |
| --- | --- | --- |
| Ответ карточки и расписание | Короткая синхронная транзакция БД | Подтверждение сервером должно означать commit результата. Уникальный ID попытки и версия состояния обеспечивают повторную доставку и правило первого ответа |
| Дата следующего повторения | Сохранённое время и запрос при открытии занятия | Отдельное задание по таймеру на каждую карточку не требуется |
| Live-разбор редактируемой фразы | HTTP, короткая пауза перед запросом, ограниченный параллелизм и частота, таймаут, проверка версии фразы | Долговечная FIFO-очередь может расходовать квоту на уже заменённые фразы. При рестарте разбор может завершиться ошибкой с возможностью повтора; подтверждённый учебный прогресс от этого не теряется |
| Ручные приглашения и восстановление | Транзакция и одноразовый токен | Обязательной фоновой доставки писем в первой версии нет |
| Корпус из 18 уроков | Подготовленный, проверенный и версионированный контент релиза | Генерация всего учебника во время пользовательского запроса не является согласованным сценарием |
| Резервные копии | Операционное расписание, контроль результата и восстановление | Прикладной брокер не является необходимым условием backup |

Пауза перед AI-запросом и отбрасывание устаревшего ответа не гарантируют отмену вычислений у провайдера. Отмена передаётся туда, где она поддерживается; лимит запросов и параллелизма действует до внешнего обращения. Произвольный фоновой `Promise` в памяти не считается гарантированно выполненной работой после рестарта.

## Когда добавлять очередь

Основание — конкретная принятая работа должна пережить разрыв HTTP и рестарт: например, будущий длительный импорт, пакетная генерация или обязательная доставка. Эти функции пока не добавлены в объём продукта.

| Вариант | Когда полезен | Что добавляет к эксплуатации |
| --- | --- | --- |
| Graphile Worker / PostgreSQL | Долговечные задания, если PostgreSQL уже выбран | Worker, схемы очереди, повторы, очистка и диагностика; по документации обработчики Node.js, совместимость с Bun не проверена |
| BullMQ / Redis | Когда нужны его возможности заданий или независимый Redis уже обоснован | Постоянный Redis, persistence/AOF, `noeviction`, лимиты истории, обработка остановки workers |
| RabbitMQ | Маршрутизация между несколькими независимыми отправителями и потребителями | Брокер, durable-настройки, persistent messages, publisher confirms, consumer acknowledgements и мониторинг |
| NATS / JetStream | Pub/sub с хранением и replay при соответствующем требовании | Core NATS сам по себе не является долговечной очередью; нужны JetStream, хранение и корректная настройка consumers |

Для будущих долговечных заданий первым исследуется PostgreSQL-очередь при уже выбранной PostgreSQL. Добавлять PostgreSQL только ради очереди при SQLite — отдельное решение. Несколько процессов на одном VPS не защищают от потери самого VPS.

Повторная доставка возможна: обработчик может совершить внешний эффект, упасть до подтверждения и получить работу снова. Нужна идемпотентность операции, особенно для обновления расписания и расходования ИИ-квоты. Наличие job ID или свойства доставки не означает однократность бизнес-эффекта.

Если одно действие должно изменить основную БД и надёжно отправить сообщение во внешний брокер, возникает задача dual write. Тогда рассматривается transactional outbox: намерение сохраняется в той же транзакции, доставка выполняется с повторами. С PostgreSQL-очередью Graphile `add_job()` можно вызывать в транзакции изменения данных; отдельный внешний dual write отсутствует. Однократный внешний эффект worker всё равно не гарантируется.

## Проверка принятого runtime перед выпуском

Проверки выполняются на принятом Hono / Bun с зафиксированными драйвером и версиями. Локальный probe подтвердил базовые операции библиотек; будущий Linux-прогон и приложение должны покрыть вход и частные запросы, конкурентный review, разбор ИИ с задержкой/отменой, SIGTERM и повтор неподтверждённой попытки. Сначала задержки приложения измеряются с управляемым ответом ИИ, затем отдельно проверяется реальный провайдер.

Записать версии, Linux/архитектуру, конфигурацию, RSS/CPU, задержки и ошибки при 10 одновременно занимающихся. Проверить таймаут, потерю соединения с БД, повтор доставки после commit, логи и остановку процесса. Готово, когда выбранный профиль сохраняет функциональную корректность, диагностируется и укладывается в измеренные ресурсы целевой среды. Поддерживать оба runtime в production не требуется.
